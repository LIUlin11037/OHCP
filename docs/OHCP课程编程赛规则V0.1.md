# OHCP 课程编程赛规则

> **OHCP** = One Hour Class Programming（课堂 90 分钟限时编程挑战赛）
>
> **适用范围**：与「课终项目评判规则 V0.2」对齐，共同面向本学期开设的  
> 「面向对象程序设计」「大数据处理技术」两门课程
>
> **文件状态**：V0.1 已确认  
> **最后更新**：2026-10-13

---

## 一、机制总览（一句话先看）

OHCP 是一场课堂现场限时编程挑战赛，固定流程为「拉群 → 发题 → 开发 → 答辩」。  
按是否参加答辩分为两档：

| 档位  | 分数范围         | 触发条件                          |
| --- | ------------ | ----------------------------- |
| 基础档 | **75**       | 所有小组必须于**下课前**提交完整项目代码 + 演讲材料 |
| 答辩档 | **80 – 100** | 小组参加答辩抢答，按评分细则给定具体分数          |

未答辩的小组即停在基础档 75 分。  
答辩档的具体分数由任课教师依据本规则 §5 维度综合判定。

---

## 二、比赛时间线

| 阶段       | 时间点            | 关键动作                                       |
| -------- | -------------- | ------------------------------------------ |
| 赛前 5 min | T-5 min        | 任课教师在课程群**拉群**（含助教、班委、各小组代表），预告本场主题        |
| 上课铃      | T 0            | 任课教师**发放比赛任务需求**到群内（含需求文档、接口/数据、评分侧重、提交规范） |
| 开发期      | T 0 → T+60 min | 各小组并行开发、完成系统测试、整理演讲材料                      |
| **答辩开放** | **T+60 min**   | 答辩环节开始，各小组按**抢答报名**模式向群内 / 任课教师报名答辩顺序      |
| 答辩进行     | T+60 min 起     | 抢答报名的小组按 §4 规则依次答辩                         |
| 下课铃      | T+end          | **所有小组**（无论是否答辩）必须于下课铃响前完成提交               |

> **关键约束**：
>
> - 答辩从 T+60 min 开始，开发不停止——未答辩/已答辩完的小组可继续打磨；
> - 但**所有小组必须于「下课铃响」前完成材料提交**，未提交者本场视为弃赛
> - 单场典型节奏（90 min 课）：拉群 5 + 开发 60 + 答辩 20 + 收尾 5

---

## 三、提交清单（基础档 75 分必备）

每个小组**必须**于下课前提交：

| 材料    | 形式                   | 必须项                        |
| ----- | -------------------- | -------------------------- |
| 项目源代码 | Git 仓库链接 / 代码压缩包     | 含 `README.md`、依赖清单、构建运行说明  |
| 演讲材料  | PPT / PDF / Markdown | 含需求理解 / 架构方案 / 关键结果 / 人员分工 |
| 测试证据  | 文本或截图                | 含核心功能点 + 是否通过              |

> 已提交即得基础档 **75 分**。**未提交或材料严重缺失**视为当场比赛弃赛。

---

## 四、答辩环节规则（OHCP 核心）

### 4.1 报名方式（按小组为单位 · 抢答报名）

- **抢答报名**：每组派 1 名代表，在 T+60 min 起向任课教师 / 课程群内**抢答报名**
  - 第一个报名的组第一个答辩，第二个第二个，依此类推
- 报名截止：通常为前一组答辩开始时即关闭；时间紧时由教师现场设定
- 同一小组不可重复报名；答辩进行中未报名的小组视为放弃答辩档机会，仍保留基础档 75 分

### 4.2 答辩时长建议（可以浮动）

| 小组规模  | 推荐演讲  | 推荐质询  |
| ----- | ----- | ----- |
| 4–5 人 | 5 min | 1 min |

### 4.3 答辩内容建议顺序

1. 需求理解（听清题意、对题目做了哪些解构）
2. 架构方案（系统怎么搭、关键模块划分）
3. 实现演示（核心功能跑通、测试覆盖情况）
4. 人员分工（谁做了什么、用时多少）
5. 系统亮点（与同侪解法相比的差异）

## 五、答辩评分细则（80 – 100 分）

### 5.1 评分维度（教师依据下表 6 维度综合参考判定）

| #      | 维度                     | 释义                            | 参考权重     |
| ------ | ---------------------- | ----------------------------- | -------- |
| 1      | **需求思考与完成度**           | 是否真听清题意；功能交付是否覆盖核心需求点         | 20%      |
| 2      | **Harness 过程与系统架构合理性** | 是否采用测试驱动 / 集成测试框架；模块划分、解耦是否合理 | 20%      |
| 3      | **功能测试覆盖率**            | 核心功能点是否均有自动化测试；测试通过率          | 15%      |
| 4      | **演讲材料质量**             | 逻辑清晰度、可视化、是否在限定时长内讲清要点        | 15%      |
| 5      | **人员分工合理性**            | 角色分配是否均衡、人尽其用                 | 10%      |
| 6      | **系统亮点**               | 与同侪解法相比是否有独到之处（创新、巧思、工程美学）    | 20%      |
| **合计** |                        |                               | **100%** |

### 5.2 分数参考刻度

| 分数      | 含义                         |
| ------- | -------------------------- |
| **80**  | 需求达成，演示完整，无明显亮点/缺陷         |
| **85**  | 达成良好，演示流畅，1–2 项突出          |
| **90**  | 达成优秀，3 项以上突出，评审认为「值得讲给下届看」 |
| **95**  | 达成极优秀，多数维度接近满分             |
| **100** | 当场比赛的最高水平，由教师酌情给出          |

## 六、特殊场景（防卡壳条款）

| 场景        | 处理                                        |
| --------- | ----------------------------------------- |
| 下课铃响时未提交  | 本场视为弃赛，不发放基础档 75 分                        |
| 答辩中材料损坏   | 教师酌情补救（如允许当场重传）；因小组失误导致丢失按现场情况判定          |
| 抢答报名时多人同时 | 由教师按小组编号或出场顺序裁定                           |
| 提交代码无法运行  | 基础档 75 分仍可发放（提交就得分），但答辩档 Harness 维度会被显著扣分 |
| 多场比赛累计    | 累计统计可用于活跃度加分 / 礼物激励；与课终成绩的关系见 §7          |

---

## 七、与其他机制的关系

- 本规则与「课终项目评判规则」**默认互相独立**：OHCP 编程赛分数用于课堂活跃度/激励，**不直接计入课终项目成绩**
- 多场比赛可累计统计（如：学期内累计得分前 3 名获额外加分/礼物）

> **[待教师确认]** OHCP 分数是否与课终成绩挂钩——如挂钩，建议方案：
>
> - 方案 A：完全独立（默认）
> - 方案 B：累计 OHCP 高分可按 N 场 → 课终基础分 +1–3 分
> - 方案 C：单场 OHCP 第一名直接获得课终基础分 +5  
>   目前暂定课终将三个环节进行综合折算
